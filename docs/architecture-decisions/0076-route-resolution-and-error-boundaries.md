# ADR-0076: Canonical route resolution and error boundaries

**Status:** Implemented on a draft PR (V1-A Increment 4, Workstream C; plan §4 Workstream C). Not yet merged or accepted.

## Context

V1-A plan §4 Workstream C (C1-C3). The generic architecture-element route, `/internal/engagements/[slug]/architecture/elements/[elementId]`, could not render a Deliverable, Review or Implementation Initiative — `RECORD_KIND_LABELS` never covered the three Phase 5 kinds — yet the app kept linking to it for those kinds: `ElementLink`, the version links in `VersionsPanel`, and the review dossier all built that same path regardless of kind. Opening any of the three there returned a 500. Separately, a non-UUID id on several internal and portal dynamic routes (the generic element page, the three record pages, baselines, Method Applications, and the portal's own element page) reached a database query before any validation, so Postgres's `invalid input syntax for type uuid` surfaced as a 500 instead of a 404. There was no `error.tsx` anywhere, so any unexpected error showed the framework's own crash page in either area, and the review dossier's query swallowed its own error and let the "Dossier" panel disappear with no sign anything had gone wrong.

## Decision

- **One canonical page per kind, one redirect, no duplicate page.** `internalElementHref(slug, kind, id)` (already used by the three record pages' own internal links) is now also where the generic element page sends a Phase 5 kind: on `GET`, before rendering, it redirects Review, Deliverable and Implementation Initiative ids to their own page, carrying a `?version=` query param forward unchanged. Every other kind still renders on the generic page, which remains its canonical home. No new page is added for any kind.
- **Direct links where the caller already knows the kind.** `ElementLink`'s `element` prop gained an optional `kind`; when present, the link targets the canonical page directly instead of bouncing through the redirect. Every existing call site already passes a `LoadedElement` or an equivalent row carrying `kind`, so this took effect with no call-site changes. The review dossier's element links do the same, using the kind the dossier's `examined` set already returns; a changed element outside that set (a dependency, say) still falls back to the generic route, which itself now redirects rather than failing.
- **The three record pages gained the read-only version view the generic page already had.** Each now accepts `?version=<id>`, looks the version up on the element it already loaded, and renders it through the same `SnapshotView` the generic page uses, factored out as `VersionSnapshotPanel` (`versions-panel.tsx`) so the markup is not duplicated.
- **Every dynamic id is format-checked before it is queried.** A `z.uuid()` check runs first on every internal and portal route that takes an element, deliverable, review, initiative, baseline or Method Application id, calling the existing `notFound()` for a non-UUID value exactly as it already did for a well-formed but unknown or foreign one. The check is a pure format test with no database access, so it changes nothing about what a malformed, unknown and foreign id each already revealed to an unauthorized caller — all three still 404 identically.
- **A calm, branded boundary for the unexpected case.** `error.tsx` and `not-found.tsx` are added for the internal area and for the client portal, each linking back into its own area and never echoing the underlying error's message. The review dossier's query now logs its failure server-side instead of swallowing it, and its panel shows "The dossier could not be prepared" instead of vanishing.
- **A production-safe way to prove the boundary in the browser suite.** `/internal/e2e-force-error` and `/portal/e2e-force-error` throw only when `E2E_TEST_ROUTES=1`, a variable `playwright.config.ts` sets on its own test server and nothing else sets; everywhere else, including a real deployment, both routes return the ordinary not-found page. Both still sit behind their area's own `requireInternal()`/`requireClient()`.

## Consequences

- No link anywhere in the app can reach a 500 for a record of any kind; the acceptance criterion in the plan's C1 is met by the redirect alone, and the direct links are an optimization on top of it, not a requirement for correctness.
- A handful of less-common generic-route links (Method Library "used on" lineage, org-wide escalations, the Bearing/History/Impact/Stewardship panels, and the Architecture Intelligence drawer's own subject links) were not changed to carry `kind` explicitly; they still route through the generic page, which redirects them correctly. Wiring these directly would mean adding `kind` to several differently-shaped rows, several of them from raw SQL aggregates, for no behavioral gain beyond skipping one redirect hop; left as a future cleanup if it is ever wanted.
- Function-only and application-only change; no table, migration or RLS change. `src/types/database.ts` is unchanged.
