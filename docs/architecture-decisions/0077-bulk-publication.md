# ADR-0077: Bulk publication

**Status:** Implemented on a draft PR (V1-A Increment 5), not yet accepted. Plan decision D8, accepted by Kerrick 2026-10-02.

## Context

Each element was published individually: open, Publish, optional note, submit, confirm, page load. A real engagement of 100 to 300 elements (Gate A requires at least 150) made this impractical, and clients see architecture only after publication, so slow publication is a real delay to the engagement, not only an inconvenience. Workstream D (V1-A plan §4) and decision D8 call for a function-only composition over the existing per-element functions, not a second publication model.

## Decision

**Composition, not a new model.** Two functions, `public.submit_elements_for_review(p_element_ids uuid[])` and `public.publish_element_versions(p_element_ids uuid[], p_change_summary text default '')`, each loop over their input and call the existing single-element function (`public.submit_element_for_review` / `public.publish_element_version`) once per id. Neither function re-implements a capability check, a lifecycle rule, record scope, methodology lineage, version numbering, snapshotting, audit, or relationship publication: every one of those still lives only in the single-element function. Individual publication is byte-for-byte unchanged; bulk publication can never disagree with it about what is allowed, because it is the same code path, called in a loop.

**Partial success, not all-or-nothing.** The plan's own "Tests" text for this workstream says it directly: "partial failure (one refused element does not block the rest)". Each element's call runs inside a nested `begin ... exception when others ... end` block. A plpgsql exception block is an implicit savepoint: on an exception, only that element's work (and its row lock) rolls back; the loop continues. Nothing commits or rolls back at the statement level — `COMMIT`/`ROLLBACK` are not legal inside a function body and are not used anywhere else in this schema. Each function returns one row per element: success (with the new version id, for publish) or the exact SQLSTATE and message the single-element function would have raised for that id alone. An unauthorized or cross-engagement id is refused as "not found" (`P0002`), the same answer the single-element RPC already gives for it; a lifecycle, scope or lineage refusal carries its own `23514` message. This per-row detail is returned only to the caller who submitted those exact ids, so it discloses nothing beyond what calling the single-element function on each id separately already would.

**Stable order and duplicates.** The input is deduplicated and sorted ascending by element id before anything is locked (`array(select distinct x from unnest(...) order by x)`). Deduplication means a repeated id is processed once: the result has exactly one row per distinct id, never one row per input position, and a repeated id cannot create two versions or two audit rows for one publish request. Ascending-id order means every bulk call — whoever submits it, whatever order its ids were selected on screen — locks an overlapping selection in the same global order, the existing deadlock-avoidance pattern this schema already uses for two-row locking (`supersede_element`'s "lock in a stable order so two supersessions cannot deadlock"). Without this, two concurrent bulk publishes over an overlapping selection — each holding its locks for the whole request, unlike separate individual-publish requests which release theirs after each element — could deadlock; sorted order rules that out. Proven in `99_architecture_concurrency` (two sessions bulk-publish the same pair in opposite input order; one waits, neither deadlocks).

**Scale, not a queue.** An array of more than 500 ids is refused outright (`23514`), before a single row is touched. V1 scale is "at least 150"; 500 is a generous ceiling against an unbounded request from the UI or a mistaken script, not a throughput target, and is well short of anything needing a background worker. No queue or worker was introduced; none is warranted at this scale.

**Accepted trade-off: a large batch briefly holds its locks.** A failed element's row lock is released immediately — PostgreSQL releases locks acquired inside an aborted savepoint. A _successful_ element's lock, taken by the single-element function's own `select ... for update`, is held until the whole bulk call's enclosing transaction commits, i.e. for the rest of the batch. A 300+ element bulk publish therefore briefly holds locks on every element it has already published, for the duration of the whole call; a concurrent attempt to individually publish one of those same elements waits for the full batch rather than for one element's worth of work. This is an availability characteristic, not a correctness or security defect — no data is at risk, and the deadlock-avoidance ordering above still holds under it (proven in `99_architecture_concurrency` case 4). Accepted as reasonable at V1 scale (one architect finishing a bulk publish in a few seconds); revisit only if evidence shows it causes real contention.

**Grants.** Both functions are `security definer`, `set search_path = ''`, revoked from `public`/`anon` and granted to `authenticated`, matching this schema's convention for sensitive functions.

**Authorization and area restrictions.** Publication authority (`publish_architecture`) and edit authority (`edit_architecture`) remain engagement-wide capabilities, unchanged by this work; bulk publication does not add, widen or sub-scope them. A user who cannot publish an element individually cannot publish it through the bulk path either, since every element's call still runs its own `require_architecture_capability`. Client-side area-limited visibility (`private.element_in_member_areas` and friends) is untouched entirely: bulk publication changes no visibility rule, exactly as single-element publication does not.

**UI.** The domain register's "All objects" table (`architecture/[domain]/page.tsx`) gained selection checkboxes on draft/in-review rows, a "select all eligible" control, a count, and "Submit for review" / "Publish" buttons, in one new client component (`ObjectRegisterTable`) reused as-is rather than a generic bulk-action framework. The action bar is rendered only for a holder of `edit_architecture` or `publish_architecture` (defense in depth; the database is still the authority). A confirmation names the count before anything is sent; a result panel afterwards names every element's outcome, with the refusal reason for any failure. The Phase 5 records register pages (reviews, deliverables, implementation) were not extended in this increment: the domain list is the realistic bulk-publish surface for "100 to 300 elements," and extending the same component to those pages, if wanted, is a small follow-up rather than part of this one.

**Server actions.** `bulkSubmitElementsForReview` and `bulkPublishElements` in `src/domain/architecture/actions.ts` follow the file's existing `run(schema, input, work)` pattern exactly, with Zod schemas capping the array at 500 client-side (the database caps it again, authoritatively).

## Consequences

- One migration (`20261011000000_v1a_bulk_publication.sql`), two new functions, no table change, no change to any existing function.
- Tests: pgTAP `63_bulk_publication` (authorized bulk publication, unauthorized refusal, cross-engagement ids, a client/area-limited attempt, an already-ineligible record, duplicate-id collapsing, audit rows, the array-size cap, empty/null input, a 150+ scale fixture, and that single-element publication is unaffected); the bulk-publish deadlock case added to `99_architecture_concurrency`. Browser: `e2e/bulk-publication.spec.ts` seeds 160 drafts directly (setup, not the tested interaction), selects and bulk-publishes them through the real UI, verifies the published state and a representative element's version/audit, verifies a Researcher is offered no bulk Publish control, and verifies single-element publication still works.
- `db:types` regenerated; the two new RPC signatures are in `src/types/database.ts`.
- Left deliberately untouched: client visibility rules, area-visibility rules, the single-element functions' bodies (aside from being called in a loop), the Phase 5 records register pages, and anything under the Architecture Intelligence Step B / Development Edge / Method Library freeze.
- Still outside this increment: a generic bulk-action framework for other record kinds (not asked for, and the plan explicitly warns against inventing one); any change to how publication affects client visibility.
